## DL-02-1 · Що є джерелом правди контракту · 2026-09-02

**Контекст.** Гра і касир ретраять. Рекрутер просить «спеку». Легко намалювати YAML або сказати «409 = немає грошей» і роз’їхатися з книгою.

| Варіант | Вердикт |
|---|---|
| OpenAPI YAML — джерело правди; імплементація потім | **Reject** — YAML без walk не фіксує TAKE/FILL і ключі |
| Лише HTTP-статус (403/409) як смисл помилки | **Reject** — 403 буває на кількох гейтах; клієнт не знає який |
| Заголовок `Idempotency-Key` окремо від `depositId` / `roundId` / `withdrawId` | **Reject for this slice** — два ідентичності, два retry-сюжети |
| Контракт = business id у тілі + успіх = snapshot столу + фейл = `{error, code, gate?}` · ключ проводки **похідний** від id (`captured:dep_1`) | **Adopt** |

**Чому.** Ідемпотентність уже в книзі. Контракт має назвати той самий id, який стає ключем. Клієнт читає `code` / `gate`, не вигадує правило зі статусу. YAML можна згенерувати з цього walk пізніше.

**Інваріант.** Повтор того ж `depositId` / `roundId` / `withdrawId` з тим самим наміром не створює другого рядка книги. Немає $ / гейт закритий → **немає рядка**, відповідь не 200.

**Переглянути, якщо** зовнішній провайдер вимагає свій `Idempotency-Key`, відмінний від round id — тоді мапінг у PAM, не другий ledger.

**Kill.** YAML-first · статус-як-спека · окремий HTTP idempotency header на цьому desk.
