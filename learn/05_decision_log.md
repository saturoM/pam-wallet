Оператор = казино (PAM). PSP A/B/C = платіжні провайдери. Банк = картка гравця.

## DL-05-1 · 3DS passed ≠ FILL · 2026-09-04

**Контекст.** Касир намалював Success після 3DS ok. Webhook `captured` ще немає. Продакт / UX: «банк уже підтвердив — пустити ставити».

| Варіант | Вердикт |
|---|---|
| Кредитити `player_cash` на 3DS success | **Reject** — автентифікація ≠ гроші |
| Кредитити на Success у касі | **Reject** — касир не пише баланс |
| FILL лише на PSP **`captured`**, ключ `deposit_id` | **Adopt** |

**Чому.** Між 3DS і capture ще мережа / PSP / банк. Інакше фантом у кишені або подвійний кредит, коли capture прийде пізніше.

**Інваріант.** `place_bet` читає лише ledger після `captured:dep_*`. 3DS ok сам по собі **0** проводок.

**Kill.** «3DS = депозит успішний» у будь-якому UI-копі як правда для балансу.

## DL-05-2 · Немає retry 3DS fail як capture · 2026-09-04

**Контекст.** `dep_1` — гравець закрив 3DS / не ввів код. Продакт: «автодотиснути capture», щоб не губити конверсію.

| Варіант | Вердикт |
|---|---|
| Мапити 3DS fail → `captured` | **Reject** — грошей немає, казино в мінусі на ставках |
| Залишити `pending` і «ще раз той самий dep_1» | **Reject** — воскресіння мертвої спроби |
| `dep_1` → **failed**; нова спроба = **новий** `deposit_id` (той самий або інший PSP / картка) | **Adopt** |

**Інваріант.** Fail 3DS = кінець цього ключа. Cascade / «спробуй ще» ніколи не переписує `dep_1` у captured без реального PSP FILL.

**Kill.** Тихий capture після fail «для метрики acceptance».

## DL-05-3 · Cascade = новий ключ після soft · 2026-09-04

**Контекст.** Soft decline на PSP-A. Routing хоче спробувати PSP-B.

| Варіант | Вердикт |
|---|---|
| Той самий `dep_1`, просто інший PSP | **Reject** — ключ і провайдер злиплись; webhook A плутає книгу |
| Два captured на один `dep_1` | **Reject** |
| `dep_1` failed; відкрити **`dep_2`** на B | **Adopt** |

**Інваріант.** Один `deposit_id` = одна спроба в одного PSP. Cascade завжди новий id. Повторний webhook по `dep_1` не «переїжджає» на B.

**Переглярити, якщо** оркестратор зовні тримає свій attempt-id — у PAM усе одно окремий `deposit_id` на кожну спробу до книги.

## DL-05-4 · Hard decline без cascade · 2026-09-04

**Контекст.** Код на кшталт `do_not_honor` / stolen card.

| Варіант | Вердикт |
|---|---|
| Cascade по всіх PSP «поки хтось не візьме» | **Reject** — фрод-спам і ризик для оператора |
| Стоп: `failed` · hard · без наступного auto-PSP | **Adopt** |
| Показати support raw код + наш статус | **Adopt** як ops (не окрема розвилка грошей) |

**Інваріант.** Карта статусів ділить soft|hard. Soft може cascade; hard — ні.

**Kill.** «Будь-який fail → наступний PSP».

## DL-05-5 · Ідемпотентність FILL · 2026-09-04

**Контекст.** Два webhook `captured` на `dep_1` з різними `evt_aaa` / `evt_bbb`.

| Варіант | Вердикт |
|---|---|
| Ключ = id доставки `evt_…` | **Reject** — повторна доставка = друга проводка |
| Ключ = **`deposit_id`** · другий captured = no-op | **Adopt** |

**Інваріант.** Одна FILL-проводка на один успішний депозит. `evt_` лише в логах / raw evidence.

## DL-05-6 · Невідомий код PSP · 2026-09-04

**Контекст.** PSP прислав `xyz_unknown` — немає в нашій карті.

| Варіант | Вердикт |
|---|---|
| Мапити в `captured` «на всяк випадок» | **Reject** — вигаданий FILL |
| Ігнорувати webhook | **Reject** — депозит зависає без стану |
| `failed` (або `pending` + алерт) · не FILL · розібрати карту / спитати PSP | **Adopt** |

**Інваріант.** Support і гейти читають **наш** статус. Невідомий raw ≠ гроші в `player_cash`.

## DL-05-7 · Hosted vs iframe (footnote) · 2026-09-04

**Контекст.** Де гравець вводить картку.

| Варіант | Вердикт |
|---|---|
| Поля картки на домені оператора | **Reject** для default — PCI scope на казино |
| Hosted / iframe PSP · desk лишається mock | **Adopt** footnote · не головна розвилка модуля |

**Інваріант.** PCI = хто торкається даних картки. Не замінює правило FILL = `captured`.

**Переглярити, якщо** продукт свідомо йде в SAQ-D — окремий рядок + security, не цей walk.
